# スライドストーリー作成スキル

ユーザーのリクエストを分析し、PPTX 生成の前段階となるスライドストーリー（構成案）を作成するスキルです。

## 重要: 出力方法

**スライド構成はチャットに直接書かず、必ず `set_scenario` ツールを使ってワークスペースパネルに送信すること。**
その際、必要に応じて **presentation-wide の `designBrief`** も含めること。

```
// 正しい方法: set_scenario ツールを呼ぶ
set_scenario({
  title: "プレゼンテーションタイトル",
  slides: [
    { number: 1, title: "タイトルスライド", bullets: ["サブタイトル"], notes: "" },
    { number: 2, title: "アジェンダ", bullets: ["トピック1", "トピック2"], notes: "" },
    ...
  ]
})

// 間違った方法: チャットにマークダウンで書く ← これはやらない
```

ツール呼び出し後、チャットには「スライド構成とデザイン方針をワークスペースに作成しました。確認してPPTX生成しますか？」のような短いメッセージだけ返す。

## いつこのスキルを使うか

- ユーザーが「プレゼンを作って」「スライドにまとめて」と依頼した場合
- 複雑なトピックや長い資料をプレゼンに変換する場合
- まずストーリーを確認してから PPTX を生成したい場合

## ストーリーテリング原則（McKinsey式）

### ピラミッド原則
1. **結論先行**: 各スライドのタイトルはそのスライドの結論・主張を述べる（疑問形や曖昧な表現は避ける）
2. **So What?**: 各スライドの `keyMessage` は「だから何？」に答える一文
3. **MECE**: トピックは漏れなくダブりなく分類する

### スライドタイトルの書き方
- ✅ 良い例: 「Azure AI で開発コストを40%削減できる」（主張が明確）
- ❌ 悪い例: 「Azure AI について」（何を伝えたいか不明）
- ✅ 良い例: 「3つの導入パターンから最適な手法を選択」
- ❌ 悪い例: 「導入パターン一覧」

### スライド枚数とストーリー責任（重要）

**枚数はユーザーが決める。1 枚でも 3 枚でも 30 枚でも、指示された枚数に従うこと。**

ただし、**「指定された枚数の中で完結したストーリーを責任を持って作る」のはあなたの仕事である。**

- **1 枚しか作らない場合**: その 1 枚に「結論・根拠・示唆」が凝縮されている必要がある。bullets は薄くてよいが `bodyMarkdown` で骨格をきっちり書く。
- **3 枚作る場合**: 3 枚で「導入 → 本論 → 結論」が成立するよう、各スライドの役割を明確にする。1 枚あたりの情報密度は単独枚数より**むしろ濃く**する必要がある（枚数が少ない＝1 枚の責任が重い）。
- **枚数指定がない場合**: トピックが成立する最小構成を提案する（多くの場合 5〜10 枚）。だが**勝手に増やさない**。

**禁止事項:**
- 枚数が少ないことを理由に各スライドを薄く作ること。**少ない枚数こそ 1 枚あたりの密度を上げる**。
- 「主な機能」「導入パターン」のような**複合トピックを 1 枚に詰め込んで bullets だけで列挙すること**。枚数が許すなら 1 項目 1 枚に展開し、枚数が限られるなら `bodyMarkdown` で各項目を文章として深掘りする。
- 情報収集（web_search + fetch）を省略すること。**枚数に関わらず**裏付けデータは必須。

### ストーリーライン構成（参考・枚数によって取捨選択）
```
1. タイトルスライド (layout: title)
   → プレゼン全体の結論を一言で

2. エグゼクティブサマリー or アジェンダ (layout: agenda)
   → 全体の流れと結論の予告

3-N. 本編 — 各セクションは以下の流れ:
   → セクション区切り (layout: section) — セクションテーマ
   → 主張スライド (layout: cards/stats/comparison) — データ・根拠
   → 詳細スライド (layout: bullets/timeline/diagram) — 具体策

N+1. Key Takeaways (layout: summary)
   → 3つの重要ポイントに絞る
```

## 実行手順（プロの思考プロトコル）

スライド作成のプロは、いきなり書き始めない。
必ず以下の 4 フェーズを順に実行し、レビュー合格までループしてから `set_scenario` を呼ぶ。

### フェーズ 1: 調査（Research）

最初に、意思決定に使える根拠を集める。**「検索結果スニペットを眺めるだけ」では不十分。**

1. ユーザー依頼から以下を確定する。
  - **トピック**: 何についてのプレゼンか
  - **対象者**: 誰向けか（経営層、エンジニア、新入社員、一般向け等）
  - **目的**: 情報共有、提案、研修、報告等
  - **スライド枚数の希望**: 指定があればそれに従う
  - **言語**: ユーザーの言語に合わせる
2. **検索 (`web_search`) を最低 3 回**、観点を変えて実施する。対象者に合わせて検索語を選ぶ（経営層→ROI / 市場規模 / 競合動向、エンジニア→アーキテクチャ / 性能 / 制限事項）。
  1. **公式情報**: 製品・サービスの公式ドキュメントや一次仕様
  2. **市場データ・統計**: 数値で裏付ける情報（市場規模、導入率、成長率等）
  3. **事例・ベストプラクティス**: 実際の導入事例や業界標準のアプローチ
  4. **批判・失敗・代替案**（提案系プレゼンの場合は必須）: 想定反論への備え
  5. **最新動向**: 新機能・アップデート・トレンド（必要に応じて追加）
3. **本文取得 (`fetch`) を最低 3 件**実施する。スニペットだけで数値を引用しない。一次資料のページを開いて文脈・前提条件・調査年を確認する。
4. **重要な数値は 2 ソース以上で三角測量**する。1 社の自社調査だけを根拠にしない。ベンダー調査 + 第三者調査、業界レポート + 公的統計など複数視点で裏取りする。
5. **2 年以内の情報を優先**し、それ以上古いソースは `notes` に「○○年時点」と明記する。
6. 使う事実は URL とセットで記録し、後段で notes に必ず反映する。
7. **十分性ルール**: 上記の最低回数はあくまで下限。トピックが複雑、データが不足、裏取りがとれていない、対象者の関心点がカバーされていない場合は、**十分な情報が集まるまで `web_search` と `fetch` を繰り返し実行する**。下記のうち 1 つでも成り立たないうちは調査を継続する：
  - 各スライドに載せる主要主張に裏付けデータが 1 件以上紐付いている
  - 提案系の場合、想定反論に対する反証/代替案を提示できる
  - 重要数値は 2 ソース以上で一致または補完している
  - 対象者の関心点（経営層なら ROI/リスク、エンジニアなら技術詳細）に答えられる材料が揃っている

逆に、十分に揃ったと判断したら調査を打ち切り、フェーズ 2 に進むこと。無限に検索し続けない。

**調査フェーズの禁止事項:**
- 検索を 1 回だけで済ませること、または検索結果スニペットのみで本文未確認のまま採用すること
- 1 ソース（特にベンダー自社調査のみ）の数値を裏取りなしで採用すること
- 一般論・推測・古い情報（3 年以上前）を、最新の事実の代わりに使うこと
- 対象者の関心と無関係な検索結果を集めて満足すること

### フェーズ 2: 設計（Plan）

次に、デッキ全体の論理構造を設計する。

1. 指定枚数の中で完結するストーリー骨子を作る。
2. 各スライドの役割を決める（例: 導入、主張、根拠、比較、結論）。
3. 各スライドごとに、載せるべき根拠データを 1-2 件ずつ紐付ける。
4. `layout` を内容に応じて仮決めする。

**設計フェーズの重要ルール:**
- 論点が重複するスライドを作らない
- 重要論点の欠落を放置しない
- 枚数が少ない場合は、各スライドの情報密度を上げる

### フェーズ 3: 執筆（Write）

設計に従い、1 枚ずつ完成させる。

1. 各スライドに `title`, `keyMessage`, `layout`, `bullets`, `bodyMarkdown`, `notes`, `icon` を埋める。
2. `bodyMarkdown` は title / section 以外で必須。内容は一般論ではなく、誰が何をどう実行するかまで書く。
3. `notes` は話者がそのまま話せる具体度で書き、必要な出典 URL を含める。
4. プレゼン全体の一貫性を保つため `designBrief` も設定する。

**執筆フェーズの禁止事項:**
- 全スライドを薄く同時に埋めること
- 出典なしの数値や断定を記載すること

### フェーズ 4: レビュー（Review）

自己採点で品質ゲートを通す。

1. 下の「コンテンツ品質チェック」を**全スライドに対して**確認する。
2. 1 つでも不合格があれば、そのスライドをフェーズ 2 または 3 に戻して改訂する。
3. 再レビューして全項目合格になったら、はじめて `set_scenario` を呼ぶ。

**レビューゲート（厳守）:**
- 不合格のまま `set_scenario` を呼ばない
- 最低 1 回は全体レビューを実施する

### 最終出力（set_scenario）

レビュー合格後にのみ出力する。

**必ず `set_scenario` ツールを使い、各スライドに以下を含める：**

| フィールド | 必須 | 説明 |
|-----------|------|------|
| `number` | ✅ | スライド番号 |
| `title` | ✅ | 結論・主張を述べるタイトル（McKinsey式） |
| `keyMessage` | ✅ | このスライドで最も伝えたい一文（So What?） |
| `layout` | ✅ | レイアウト種別（下記参照）。**後段のPPTX生成で再解釈してよいヒント** |
| `bullets` | ✅ | コンテンツ項目（**4〜6 項目を推奨。最低 3 項目**。各 bullet は 15〜40 文字の具体フレーズ。「〜が重要」のような一般論は避け、「〜は前年比40%増加（出典: Gartner 2025）」のように裏付けを示す） |
| `bodyMarkdown` | ✅ 準必須 | **スライド本体の精緻な本文。日本語なら 600〜1200 文字（英語なら 350〜700 語）、3〜5 段落。** `bullets` は見出し、`bodyMarkdown` が身。**subheading（`## xxx`）・太字（`**xxx**`）・具体的な数値・固有名詞・年号・出典・対比（before/after, 競合比較）を必ず含める**。一般論や抽象論ではなく「誰が／何を／いつ／いくらで／どう実現するか」「なぜそれが今重要か」「対象者が次に何をすべきか」まで踏み込む。**画像生成（image-then-pptx モード）では gpt-image-2 がこの本文を読んで構図・チャート・テキスト要素を決定するため、本文が薄いと画像は一般的なストック画像風になり、固有の数値や日本語コピーが画像内に現れない。**「リサーチノート」として gpt-image-2 に十分な素材を渡すつもりで、調査フェーズで得た事実をここに惜しまず投入する。title / section divider スライド以外は必ず埋める。スピーカーノートとは別物。 |
| `notes` | ✅ | スピーカーノート（**全スライド必須、空欄・ダッシュ禁止**。話すべき内容を 3〜5 文・150 文字以上で具体的に記載。Web検索で得た情報がある場合は出典URLも記載） |
| `icon` | - | アイコン名 |

さらに、**プレゼン全体のデザイン意図**を `designBrief` に入れることを強く推奨する。

### designBrief の考え方

`designBrief` は PPTX 生成時のアートディレクションであり、各スライドの `layout` より上位の意図を表す。

| フィールド | 説明 |
|-----------|------|
| `objective` | 全体として何を感じさせたいか |
| `audience` | デザイン上の主対象 |
| `tone` | 例: executive, premium, analytical, bold |
| `visualStyle` | 例: editorial cards, minimalist dashboard, keynote-style hero |
| `colorMood` | 配色のムード |
| `density` | airy / balanced / dense（デフォルトは **balanced** だが、ビジネスプレゼンでは **dense** 寄りを推奨。スカスカなスライドは避ける） |
| `layoutApproach` | structured / hybrid / design-led（デフォルトは **hybrid**。AI の創造的な再解釈を許容する） |
| `directions` | 守ってほしいデザイン指示を箇条書き |

### レイアウト種別

| layout | 用途 | 構造 |
|--------|------|------|
| `title` | タイトルスライド | 大きなタイトル + サブタイトル |
| `agenda` | アジェンダ / サマリー | 番号付き項目リスト |
| `section` | セクション区切り | 大きなテキスト + アクセントバー |
| `bullets` | 箇条書き説明 | タイトル + 箇条書き |
| `cards` | 複数項目の並列表示 | 2-6枚のカード |
| `stats` | 数値・統計ハイライト | 大きな数値 + ラベル |
| `comparison` | 比較・Before/After | 2-3列の比較表 |
| `timeline` | 時系列・ステップ | 横並びフロー |
| `diagram` | 概念図・アーキテクチャ | 自由レイアウト |
| `summary` | まとめ・Key Takeaways | 重要ポイント 3つ |

### 利用可能アイコン

`arrow-trending-up`, `brain`, `building`, `calendar`, `chart`, `checkmark-circle`, `cloud`, `code`, `data-trending`, `document`, `globe`, `lightbulb`, `link`, `lock-closed`, `money`, `people-team`, `rocket`, `search`, `settings`, `shield`, `sparkle`, `star`, `target`, `warning`

**各スライドに適切なアイコンを1つ割り当てること。** ただしこれは厳密な実装指示ではなく、デザインのヒントである。

## 言語ルール

- ユーザーの言語に合わせてスライドを作成する
- 専門用語は原語を併記する（例: 「検索拡張生成（RAG）」）
- サービス名・製品名は公式名称をそのまま使用する

## コンテンツ品質チェック

- [ ] **指定された枚数の中でストーリーが完結している**（1 枚なら 1 枚、3 枚なら 3 枚で導入→本論→結論が成立）
- [ ] **枚数が少ない場合ほど 1 枚あたりの情報密度が高い**（薄いまま枚数を減らしていない）
- [ ] **複合トピック（「主な機能」「ユースケース」等）を 1 枚に bullets だけで列挙していない**（枚数が許せば分割、許さないなら `bodyMarkdown` で文章として深掘り）
- [ ] 各スライドのタイトルが結論・主張を述べている（疑問形や曖昧な表現でない）
- [ ] **各コンテンツスライドの `bodyMarkdown` が 600〜1200 文字（英語なら 350〜700 語）・3〜5 段落で記載されている**（title / section divider は除く）
- [ ] **`bodyMarkdown` に subheading（`## xxx`）・太字・具体的な数値が含まれている**
- [ ] 箇条書きが 4〜6 項目で、具体的な数値・データが含まれている
- [ ] スピーカーノートが 3〜5 文・150 文字以上で具体的
- [ ] 対象者に適した用語レベル
- [ ] web_search を最低3回実施し、観点を分けて情報を裏付けている
- [ ] fetch で本文を最低3件取得し、スニペットだけで判断していない
- [ ] 重要な数値は2ソース以上で三角測量している（単一ベンダー調査のみで断定していない）
- [ ] 引用情報は2年以内が中心で、古い場合は「○○年時点」と notes に明記している
- [ ] notes に出典URL（Web検索・fetchで得た場合）を記載している
- [ ] 一般論・推測ではなく、検索・本文確認で得た事実に基づいている
